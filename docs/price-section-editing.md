# Price Section Editing

Этот файл нужен, чтобы правки блока цен не превращались в повторный разбор Tilda export и долгую визуальную проверку.

## Current Rule

Дизайн блока цен считается сохраненным. Для следующих правок по умолчанию менять только:

- тексты внутри уже созданных Astro-переменных;
- маленькие CSS-параметры внутри `priceSectionAssets`;
- подписи вкладок в `priceBodyWithText`;
- порядок, видимость или размеры только если владелец прямо попросил.

Не пересобирать блок заново. Не заменять Tilda records. Не делать новый layout вместо текущего.

## Current Price Layout Notes

Первая вкладка использует кастомную сетку:

```css
.tg-price-formats{
  grid-template-columns:.46fr .54fr;
}
```

Это сделано, чтобы разделитель стоял визуально симметричнее, а `Классическая свадьба` помещалась в одну строку на обычном desktop viewport.

Вкладки используют родную Tilda-плашку фоном/рамкой. Не добавлять отдельные рамки на каждую кнопку: это превращает меню в три прямоугольника и ломает оригинальный вид.

## Fast Change Recipes

### Поменять текст тарифа

Править только `priceFormatsMarkup`. После изменения:

```bash
npm run build
git add src/pages/index.astro
git commit -m "Update price copy"
git push origin HEAD:main
npm run verify:pages -- --contains "новый текст" --absent "старый текст"
```

### Поменять список "Что входит"

Править `priceValueMarkup`. Если меняется нижнее пояснение - `priceFineprintMarkup`.

### Поменять текст консультации

Править `priceConsultationMarkup`.

### Чуть подвинуть абзац или строку

Сначала искать CSS-класс внутри `priceSectionAssets`. Обычно достаточно изменить `margin`, `padding`, `font-size`, `line-height`, `width` или `top` конкретного Tilda `data-elem-id`.

Не запускать browser/MCP/headless автоматически. Владелец проверяет визуально после live deploy.

## Required Check For Simple Edits

Для обычных правок блока цен:

```bash
npm run build
```

После push:

```bash
npm run verify:pages -- --contains "ключевой новый текст" --absent "ключевой старый текст"
```

Полная browser/headless проверка нужна только если:

- меняется высота record;
- меняются контакты/CTA;
- меняется поведение вкладок;
- владелец прямо просит проверить viewports автоматически.

## Why The Previous Iteration Was Slow

Ошибка процесса была в том, что мелкая правка текста и CSS была обработана как редизайн секции с полной визуальной автоматизацией. Это привело к лишней пересборке структуры, конфликту с оригинальной Tilda-механикой и долгим проверкам через preview/headless.

Правильный процесс для этого блока: минимальный diff -> build -> commit -> push -> live marker-check -> ручная визуальная проверка владельцем.
