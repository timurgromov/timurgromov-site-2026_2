# Quick Edit Playbook

Короткая инструкция для следующих чатов и мелких правок. Цель - не изучать Tilda export заново и не тратить несколько итераций на простые сдвиги.

## Почему правки тут могут быть медленными

Главная страница - это не обычная ручная верстка. Это Tilda Zero Block export внутри Astro. Большинство элементов стоят абсолютными координатами и имеют отдельные значения под брейкпоинты `1920`, `1200`, `640`, `320`.

Из-за этого простое "подвинь строку" технически означает:

1. найти правильный `rec...`;
2. найти правильный `data-elem-id`;
3. проверить desktop/tablet/mobile, потому что координаты разные;
4. убедиться, что Tilda runtime после загрузки не пересчитал блок иначе;
5. не задеть соседние элементы, которые тоже стоят абсолютными координатами.

Если править только один viewport или только один `top`, сайт может выглядеть нормально первые секунды или на одном экране, но поплыть на другом.

## Быстрый алгоритм любой визуальной правки

1. Прочитать `AGENTS.md`, этот файл и `docs/tilda-zero-editing.md`.
2. Перед правками тонких/ломких мест обязательно прочитать `docs/do-not-break-this-site.md`.
3. Найти текст/элемент через `rg` по `files/page62008353body.html` и `src/pages/index.astro`.
4. Зафиксировать `rec...` и `data-elem-id` элемента и соседей.
5. Править минимально в `src/pages/index.astro`, в CSS override или Tilda-like injected markup.
6. Для обычной правки текста, цены, CSS-состояния, вкладки или небольшого блока не запускать тяжелые проверки автоматически. Быстрый минимум: `npm run build` и текстовый grep/`verify:pages` по нужным маркерам после push.
7. Если это контакты, popup, меню, телефон, Telegram/MAX, Instagram/VK или footer - выполнить профильную проверку, но не расширять ее до дополнительных browser/MCP сценариев без прямой просьбы владельца.
8. Commit, push именно в `main`, дождаться автодеплоя `gh-pages`, проверить опубликованный HTML маркерами и отдать владельцу на визуальную проверку.
9. Если запускались browser/headless/preview проверки, закрыть тестовые процессы.
10. Если push был только в рабочую ветку, сайт не обновлён. Для live-задач это незавершённая работа.

Критичное уточнение:

- `npm run build` в этом режиме - только локальный preflight.
- Нельзя завершать site-task после `build`, если пользователь не попросил остановиться до публикации.
- Для живого сайта короткий цикл всё равно заканчивается только так: `build -> commit -> push -> verify:pages/live-check`.

## Codex Sandbox Rule

В текущем Codex окружении команды, которые поднимают локальный сервер, открывают headless Chrome или читают список процессов, часто требуют escalated permissions.

Типовые симптомы:

- `listen EPERM: operation not permitted 127.0.0.1:<port>` при `npm run verify:contacts` или `npm run preview`;
- `operation not permitted: ps` при cleanup-проверке процессов;
- DNS/network ошибки при live-проверках GitHub/production.

Это не означает, что сайт сломан. Это ограничение managed sandbox.

Правило:

- `npm run verify:contacts` запускать сразу с escalated permissions, потому что он всегда поднимает `astro preview` и headless Chrome.
- `ps aux | egrep ...` для cleanup тоже запускать с escalated permissions, если обычный запуск запрещён.
- `npm run verify:pages` / `git ls-remote` / live `curl` к `timurgromov.ru`, `timurgromov.github.io`, `github.com` запускать сразу с escalated permissions, когда это финальная production/live-проверка после push. Не делай сначала заведомо падающий sandbox-прогон.
- Не тратить время на повтор одного и того же sandbox-запуска после `EPERM`; это ожидаемый отказ среды, а не диагностический сигнал по сайту.

## Visual Proof Rule

Для задач формата `сделай как раньше`, `уменьши кнопки`, `слишком большие`, `слишком громоздко`, `подгони под дизайн`, `по скрину должно быть ближе` не нужно автоматически включать тяжелую визуальную проверку на каждом проходе.

Базовый режим:

- `npm run build`
- `git push origin main`
- `npm run verify:pages`

Это подтверждает код и публикацию. Для многих мелких правок этого достаточно, если владелец сам быстро смотрит live.

Самостоятельный visual-check обязателен только если:

1. правка затрагивает UX-рискованную зону: popup, формы, контакты, footer, hero, video, сложную адаптивность;
2. владелец прямо попросил проверить на нескольких экранах или сверить по скрину;
3. агент сам видит высокий риск, что без live-проверки можно соврать про результат.

Если visual-check нужен, сначала проверять страницу именно в Browser / in-app browser Codex. Это основной и предпочтительный способ для UX и дизайна, потому что он быстрее и ближе к реальному просмотру, чем цепочка из внешних скриншотов и обходных automation-сценариев.

Жёсткое правило для UX-подтверждения:

- если агент пишет `вижу`, `кнопки на месте`, `выглядит нормально`, `совпадает`, это должно быть подтверждено тем же самым состоянием, которое реально видно в Codex browser;
- нельзя подтверждать UX по одному состоянию DOM/CSS и одновременно показывать пользователю другой экран;
- нельзя оставлять принудительный viewport override (`1911px`, `1440px`, mobile preset и т.п.) внутри узкой видимой панели и потом делать выводы по тому, что пользователь видит глазами;
- перед финальным UX-утверждением нужно либо:
  1. сбросить viewport override и проверить видимый экран в Codex browser;
  2. либо явно написать, что проверка сделана в невидимом/техническом viewport, и не выдавать это за визуально подтверждённый факт;
- если видимый Codex browser показывает расхождение со словами агента, приоритет у видимого экрана, а не у численных измерений.

Использовать headless-скриншоты, `verify:*`, Playwright и прочие автоматические проверки как дополнение или fallback:

1. когда нужно численно подтвердить состояние;
2. когда надо проверить несколько viewport по шаблону;
3. когда in-app browser не даёт надёжно снять состояние;
4. когда задача не про субъективный UX, а про техническую регрессию.

Если visual-check не делался, допустимы два честных формата ответа:

1. `деплой подтвержден, визуально посмотри live`;
2. `деплой подтвержден, по коду изменено вот это: ...`, с numeric before/after.

Запрещенный паттерн:

- писать `готово`, если подтвержден только деплой;
- писать `кнопки стали компактнее`, не показывая ни visual proof, ни numeric deltas.
- писать `кнопки на месте`, когда в видимом Codex browser они отсутствуют или схлопнуты.

## Fast Visual Edit Mode

Для простых визуальных правок, где владелец сам смотрит результат глазами, использовать короткий цикл:

1. Прочитать конкретный участок кода и карту `rec...`/`data-elem-id`.
2. Сделать минимальный diff.
3. Запустить только `npm run build`.
4. Проверить HTML/тексты быстрым `rg` или `npm run verify:pages` после публикации.
5. Commit -> push в `main` -> дождаться Pages.
6. Написать владельцу: что изменено, ссылка на live, что именно проверить глазами.
7. Если задача была субъективная по ощущению (`аккуратнее`, `меньше`, `как раньше`), отдельно сказать: visual-check делался или нет; если не делался, дать владельцу короткий live-check prompt.

Отдельно:

- шаг `3. npm run build` не является финишем;
- если агент остановился после `build`, задача по живому сайту считается недоведенной;
- исключение только одно: владелец прямо попросил пока не коммитить/не пушить.

Не делать в этом режиме:

- не запускать тяжелую automation-цепочку без причины;
- не снимать headless-скриншоты;
- не запускать много viewport-проверок;
- не блокировать push ожиданием идеальной автоматической визуальной проверки.

Исключения: контакты, popup/menu, footer, видео/Safari, hero poster, формы, якоря и явно рискованные изменения. Там допускается профильная автоматическая проверка, но только по задаче, без расширения объема.

## Design Preservation Mode

Если владелец говорит "оставить дизайн", "как было", "в той же концепции", "только текст поменять", это означает:

1. Не заменять Tilda record целиком.
2. Не придумывать новую композицию, новые карточки, новые сетки и новую механику.
3. Сначала найти существующий `rec...`, `data-elem-id`, CSS override или уже созданную Astro-переменную с контентом.
4. Менять самый маленький слой:
   - текст в существующем replacement-массиве;
   - CSS-параметр: `font-size`, `line-height`, `margin`, `padding`, `width`, `grid-template-columns`;
   - порядок или видимость только если это прямо попросили.
5. После правки не запускать расширенную визуальную автоматизацию. Сделать `npm run build`, push, live marker-check и попросить владельца посмотреть.

Запрещенный паттерн: "раз просьба про блок, пересоберу весь блок своим HTML". Это уже редизайн, даже если цвета и фото похожи.

Если непонятно, какой слой менять, остановиться и написать владельцу коротко: "это правится текстом / CSS / структурой, выбираю минимальный вариант".

Если всё-таки нужен новый кастомный блок, правило для этого сайта жёсткое:

1. Не рисовать новый блок "в похожем стиле".
2. Не собирать новую композицию по памяти.
3. Найти на сайте уже существующий аналогичный паттерн.
4. Копировать именно его полный паттерн: markup, classes, helper-функции, CSS variables, breakpoints, split-buttons, headline pattern, spacing logic, assets, state-классы и hover-механику.
5. Менять только copy, ссылки, IDs и минимально необходимую геометрию.
6. Если после копирования паттерн не применился из-за Tilda cascade, basePath, CSS parser issue или порядка стилей, чинить эту техническую причину. Не заменять копию на "похожую" самодельную верстку.

Если аналог не найден, это не повод импровизировать. Нужно коротко остановиться и согласовать новый паттерн с владельцем до реализации.

Жёсткое толкование:

- `как на сайте`, `в том же стиле`, `такая же верстка`, `такие же кнопки`, `возьми готовое`, `скопируй паттерн`, `не заново` = literal copy-first.
- Нельзя брать только цвета, шрифты и примерный ритм, а затем собирать новый HTML/CSS. Это редизайн.
- Нельзя переписывать готовый split-button, карточку, CTA или сетку "чуть проще". Сначала должна быть копия уже работающего паттерна.
- Перед правкой нового кастомного блока агент должен найти и зафиксировать источник копирования: файл, function/const, `rec...` или CSS/class pattern.

## Source-First Protocol

Перед любой заметной правкой блока, CTA, карточек, popup, mobile layout или механики агент обязан пройти такой протокол:

1. Найти на сайте готовый аналог не только по внешнему виду, но и по поведению.
2. Зафиксировать canonical source:
   `Источник: src/pages/index.astro -> planCtaSectionMarkup -> .tg-plan-cta`
   или
   `Источник: files/page62008353body.html -> rec862070380 -> mobile horizontal scroll`
3. Скопировать именно этот source целиком.
4. Менять только content, hrefs, IDs и минимальную геометрию.
5. Если копия не заработала, чинить причину, почему она не применилась.
6. Не заменять копию на "похожую упрощённую реализацию".

Для механик действует отдельное ужесточение:

- Если на сайте уже есть horizontal scroll, slider, swipe row, popup behavior, sticky behavior, split-button behavior или hover reveal, нужно переиспользовать именно эту механику.
- Запрещено писать вторую механику "с тем же смыслом", если первая уже есть и доступна для копирования.
- Если найдено два аналога, нужно выбрать один canonical source и не смешивать решения по памяти.

Обязательный формат первого рабочего апдейта для таких задач:

- `Источник: <файл/record/helper/class>`
- `Копирую: <что именно переносится>`
- `Меняю только: <copy/links/IDs/min geometry>`

## Anti-Cascade Protocol

Это правило добавлено после длинной цепочки regressions на `/materials/`, где простые задачи растянулись из-за компенсирующих фиксов поверх уже неверной базы.

Перед любой UX-правкой, где есть риск geometry, stacking или cascade, агент обязан в первом рабочем апдейте явно зафиксировать:

- `Источник: <canonical source>`
- `Ломается: <один конкретный симптом>`
- `Причина проверяется в слое: <markup / CSS rule / overlap / record height / viewport state>`
- `Не трогаю: <что не должно меняться>`

Рабочий порядок:

1. Не начинать с "подвинуть пока похоже".
2. Сначала определить тип дефекта:
   - source pattern не скопирован;
   - pattern скопирован, но не применился;
   - соседний Tilda layer перекрывает блок;
   - record слишком высокий или низкий;
   - viewport check не совпадает с тем, что реально видит владелец.
3. Исправлять только этот причинный слой.
4. Сразу перепроверять именно этот симптом.
5. Только потом переходить к следующей жалобе.

Запрещённые компенсирующие паттерны без отдельного доказательства:

- fallback button styles поверх уже существующего canonical CTA pattern;
- отрицательные `margin-top` / `margin-bottom` между records ради "поджать gap";
- desktop-only или mobile-only hardening, если причина ещё не локализована;
- новый кастомный layout поверх Tilda record, если можно починить existing source pattern;
- утверждения `всё на месте` по DOM/CSS, если visible browser frame показывает другое.

Если всё же нужен hard fix (`!important`, forced height, forced visibility, `z-index`, `overflow:hidden`), агент обязан:

- коротко объяснить, какой дефект он нейтрализует;
- проверить, не появился ли соседний side effect;
- записать это в worklog как hardening layer, а не как "обычную правку отступа".

## CTA Button Style Rule

Если владелец просит добавить или поправить CTA-кнопки в новых кастомных блоках или popup, использовать общий split-button pattern `tg-tilda-cta` из `src/site/tilda-cta.ts`.

Эталон из Tilda export: `rec862529266`, кнопка `смотреть больше`. Это не один прямоугольник: слева отдельная скругленная плашка, справа отдельный скругленный квадрат со стрелкой, поверх них общий кликабельный слой.

Не рисовать заново generic rounded button с псевдо-стрелкой. Не обнулять внутренние скругления между левой частью и квадратом. Детальное правило и ID слоев лежат в `docs/do-not-break-this-site.md` в разделе `CTA Split Button Rule`.

Для CTA копировать не только class names, а весь рабочий комплект: `tildaCtaInner`, `tildaCtaLink` / `tildaCtaButton` из `src/site/tilda-cta.ts`, `.tg-tilda-cta`, `.tg-plan-cta__button`, CSS variables, media queries, SVG mask URL и hover rules. После сборки проверить, что compiled CSS не сломан и браузер реально видит правила `.tg-plan-cta__button` / `.tg-plan-cta__item`, а не только базовый `.tg-tilda-cta`.

## Что проверяет страховка контактов

`npm run verify:contacts` собирает сайт, запускает preview, открывает отдельный headless Chrome и проверяет `1911x1064`, `1440x900`, `390x844`.

В Codex managed sandbox эту команду запускать сразу с escalated permissions. Обычный sandbox часто запрещает bind локального preview-порта и даёт `listen EPERM`; после разрешения тот же тест должен выполняться нормально.

Проверка ловит:

- Telegram/MAX отсутствуют, серые или уехали;
- строка контактов пересекает телефон или соцсети;
- MAX обрезан справа;
- стрелка и Instagram/VK не выровнены;
- Instagram/VK слишком далеко друг от друга;
- мобильный popup уводит телефон слишком низко;
- скрытые пункты popup снова видны;
- мобильная почта отсутствует или слишком далеко от соцсетей;
- мобильное footer menu растянуто или залезает на ИП/ОГРНИП/ИНН.

## Быстрый sanity-check после проверки

```bash
ps aux | egrep "contact-layout-chrome|remote-debugging-port=|headless=new|astro preview|npm run preview" | grep -v egrep
```

Если команда ничего не выводит - тестовых процессов нет.

## Быстрый deploy-check

Публичный сайт обновляется автоматически только после push в `main`: workflow `.github/workflows/deploy-gh-pages.yml` собирает `dist/` и пушит его в ветку `gh-pages`.

Минимальная команда после публикации:

```bash
npm run verify:pages -- --contains "текст, который должен появиться" --absent "старый текст, который должен исчезнуть"
```

Для блока цен пример:

```bash
npm run verify:pages -- --contains "Два понятных формата" --contains "145 000 ₽" --absent "105 000 ₽ / 125 000 ₽" --absent "Пн - Чт"
```
